# ADR-0001: Использование Clean Architecture с DDD

## Статус

Принят

## Контекст

Проект OrderPaymentSystem требует поддерживаемой, тестируемой архитектуры, которая:
- Разделяет бизнес-логику от инфраструктурных забот
- Позволяет независимо тестировать доменную логику
- Обеспечивает лёгкую эволюцию технологий
- Следует лучшим практикам industry для .NET приложений

## Решение

Мы принимаем Clean Architecture (Onion Architecture) с элементами Domain-Driven Design:

### Структура слоёв

```
Domain (Центр)
  - Сущности, Value Objects, Доменные ошибки
  - Нет зависимостей от других слоёв

Application
  - Use Cases, Сервисы, Спецификации, DTOs
  - Зависит только от Domain

Infrastructure
  - EF Core, Репозитории, Внешние сервисы
  - Зависит от Domain и Application

Presentation (Снаружи)
  - Контроллеры, Мидлвары, Конфигурация
  - Зависит от всех внутренних слоёв
```

### Ключевые паттерны

1. **Богатые доменные модели**: Бизнес-логика инкапсулирована в сущностях
2. **Result Pattern**: Типобезопасная обработка ошибок без исключений
3. **Specification Pattern**: Инкапсулированная логика запросов
4. **Repository Pattern**: Абстракция доступа к данным
5. **CQRS-lite**: Раздельные операции чтения/записи где выгодно

### Правило зависимости

Зависимости исходного кода могут указывать только внутрь. Ничто во внутреннем круге не может знать что-либо о внешних кругах.

## Последствия

### Позитивные

- **Тестируемость**: Доменная логика может быть протестирована без инфраструктуры
- **Независимость**: Бизнес-правила изолированы от изменений технологий
- **Гибкость**: Легко заменить реализации (например, базы данных)
- **Ясность**: Чёткое разделение забот

### Негативные

- **Сложность**: Больше слоёв и шаблонного кода
- **Кривая обучения**: Требуется понимание Clean Architecture
- **Накладные расходы**: Больше файлов и абстракций для простых функций
